> **Supuesto:** los drivers de arquitectura se derivaron de `requirements.md`. Si el equipo usa otro conjunto, deben reemplazarse las filas de la matriz y recalcularse los totales.

## Tarea 1 · Comparación de estilos

En los tres estilos, el servidor MCP de la semana 4 corre como proceso independiente. Pesos: alta ×3, media ×2, baja ×1.

| Driver (peso) | (a) Monolito SSR | (b) Servicios HTTP | (c) API + SPA |
| --- | --- | --- | --- |
| D1 Determinismo y trazabilidad, RNN-01/08 (alta ×3) | **5**: pipeline y `match_registro` en una transacción | **3**: registro distribuido; fallos parciales entre servicios | **5**: mismo backend que (a) |
| D2 Frontera LLM con respaldo, RNN-02/10 (alta ×3) | **5**: validador y plantilla en proceso, sin red extra | **4**: aislamiento claro, pero más saltos y timeouts | **5**: idéntico a (a) en backend |
| D3 Consentimiento, atributos protegidos, OSE agregada, RNN-04/06/09 (alta ×3) | **5**: servidor decide qué renderiza cada rol | **3**: verificación de consentimiento duplicada entre servicios | **4**: JSON por rol arriesga sobreexponer campos |
| D4 Degradación con MCP/RAG caídos, Req 1.10, 2.8–2.9 (media ×2) | **4**: un orquestador combina ambos avisos | **3**: timeouts encadenados complican avisos simultáneos | **4**: igual a (a); SPA solo muestra avisos |
| D5 Simplicidad para el plazo académico (media ×2) | **5**: un repositorio, un despliegue, sin build JS | **2**: varios despliegues, contratos y red | **3**: dos bases de código, CORS, build |
| D6 Testabilidad (media ×2) | **4**: funciones puras; vistas HTML menos directas | **3**: exige pruebas de contrato entre servicios | **4**: TestClient sobre API; SPA aparte |
| D7 Interactividad del portal multirrol (baja ×1) | **3**: suficiente para formularios y tablas | **3**: depende del frontend elegido | **5**: interfaz rica y reactiva |
| D8 Escalado independiente (baja ×1) | **2**: escala completo | **5**: escala por capacidad | **3**: frontend y API separados |
| **Total ponderado (máx. 85)** | **76** | **54** | **72** |

No hay empate. La diferencia entre (a) y (c) es estrecha y se concentra en D3 y D5.

### Recomendación

Adoptar (a): un monolito modular en FastAPI, con plantillas renderizadas en servidor y el MCP como proceso aparte. Gana en los tres drivers altos y en simplicidad. Conviene organizar los routers en dos capas, `/api` en JSON y vistas HTML que la consumen internamente, para que migrar a (c) sea barato.

**Condición de revisión:** si aparece un consumidor externo de la API (una app móvil u otro sistema de la UNDC), o si la interactividad requerida supera formularios y tablas, migrar a (c) sin tocar el backend.

### Frontera del modelo de lenguaje

El módulo `explicacion` vive dentro del monolito y se invoca después de que filtro, puntaje y ruta fijaron el puntaje y la huella. Recibe la estructura sin nombre, código ni atributos protegidos. El puerto `Redactor` (Gemini → Groq → plantilla) devuelve solo texto, y el `Validador` lo acepta o lo sustituye. Ningún cálculo lee esa salida.

## Tarea 2 · ADR-001: Orquestación del agente y frontera del modelo de lenguaje

**Estado:** Propuesto (semana 4).

### Contexto

D1 (determinismo) y D2 (frontera del LLM) son drivers de prioridad alta. RNN-01 y RNN-02 prohíben que un modelo calcule, ordene o seleccione cursos. RNN-08 exige una huella reproducible. RNN-10 y Req 9 exigen operar sin claves. Req 3.6 impone un respaldo asimétrico: se pasa a Groq solo ante un 5xx o un fallo de conexión de Gemini, nunca ante un timeout. FastAPI y MySQL (XAMPP) ya están fijados, y el MCP corre como proceso aparte.

### Alternativas

Todas las dependencias se consideran en "versión estable vigente" [VERIFICAR].

|  | (1) Flujo propio en Python | (2) LangChain / LangGraph | (3) Tool calling nativo |
| --- | --- | --- | --- |
| **¿Quién decide el orden?** | El código del orquestador | El grafo en código; los nodos-agente ceden el control al modelo | El modelo |
| **¿Reproducible sin red?** | Sí: puntaje, huella y plantilla son locales | Solo si todos los nodos son deterministas | No; sin claves no hay flujo |
| **Dependencias [VERIFICAR]** | Cliente MCP, httpx, SDKs Gemini/Groq opcionales | langgraph, langchain-core, integraciones Gemini/Groq/MCP | SDKs Gemini/Groq con herramientas, cliente MCP |

- **(1)** Ventajas: cumple RNN-01/02 por construcción, codifica explícitamente el respaldo asimétrico de Req 3.6 y se prueba con pytest sin simular el framework. Desventaja: reintentos, timeouts y trazas se escriben a mano.
- **(2)** Ventajas: estado tipado y grafo inspeccionable. Desventajas: añade una capa para un flujo lineal de cuatro pasos, y sus respaldos genéricos suelen activarse también por timeout, lo que contradice Req 3.6 [VERIFICAR]. Su API cambia con frecuencia.
- **(3)** Ventaja: casi no requiere código de orquestación. Desventaja: el modelo elegiría qué cursos consultar, lo que viola RNN-02 y RNN-05; además, la huella no es reproducible y se incumple Req 9.

### Decisión

Adoptar (1). La función `pipeline.ejecutar()` recorre etapas fijas: filtro → puntaje → ruta (MCP + RAG) → explicación. El puerto `Redactor` tiene adaptadores Gemini, Groq y Plantilla, y el `Validador` es obligatorio. `VERSION_PIPELINE` es una constante semántica.

### Consecuencias

- **Positivas:** el puntaje y la huella no dependen de red ni de claves, y `explicacion_origen` siempre es determinable.
- **Negativas:** hay que mantener timeouts y respaldo propios.

### Deuda aceptada

XAMPP incluye MariaDB [VERIFICAR], donde JSON es un alias de LONGTEXT y no existe JSONB (RNN-08). Se usará JSON validado hasta migrar a PostgreSQL. No habrá trazas distribuidas, solo logging estructurado propio.

### Criterio de reversión (antes de la semana 7)

Migrar a (2), limitada a LangGraph con nodos deterministas, si al cierre de la semana 6 ocurre cualquiera de estas dos situaciones:

- el orquestador no pasa las pruebas de Req 1.10, 2.8–2.9, 3.6–3.7 y 9.4;
- la lógica de control (ramas de degradación y reintentos) supera en líneas a la lógica de negocio.

La alternativa (3) queda descartada sin reversión mientras rijan RNN-01 y RNN-02.
